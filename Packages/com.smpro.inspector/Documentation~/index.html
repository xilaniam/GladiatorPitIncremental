SMInspectorPro

Attribute-driven inspectors for Unity 6. Put attributes on your fields and methods and get grouped layouts, conditional fields, buttons, validation, richer value pickers, tables and tool windows, without writing editor code. Classes that use none of its attributes keep Unity's default inspector, unchanged.

Unity 6000.0+ Dependencies none Attributes 40 Tests 170 edit-mode Refresh GC 0 allocations

What it offers

Everything runs on UI Toolkit and Unity's own serialization. Removing the package never loses data: attributes are plain metadata, and the one serialized type it adds stores an ordinary list.

Layout

Boxes, foldouts, tabs, rows and columns that nest by path, plus titles, info boxes, labels, suffixes and indents.

Conditions

Show, hide, enable or disable fields from a bool, an enum, a value or a method. Groups hide when all their fields are hidden.

Buttons and members

Methods become buttons with fields for their parameters. Properties and private fields can be shown read-only. Methods can run when a value changes.

Validation

Required references, custom rules, limits that clamp, asset or scene restrictions, and rules across fields, shown under each field.

Project validator

Scan open scenes, build scenes, prefabs and assets with the same rules. Optional build check and a command-line entry for CI.

Value pickers

Dropdowns from members, enum buttons, draggable progress bars, range sliders, previews and file or folder paths.

Lists and tables

Attributes work inside list elements. Element labels, add, remove and drag settings, tables for class lists, and a serializable dictionary.

Polymorphism

A type picker for [SerializeReference] fields, and inline editors for referenced assets.

Tool windows

SMEditorWindow draws a window from its fields. SMMenuWindow adds a searchable tree menu for databases.

Extensible

Every attribute is one attribute class and one handler class. A project's handler replaces a built-in one for the same attribute.

How it works

A fallback editor checks whether a type uses any SMInspectorPro attribute. If it doesn't, Unity's default inspector is built, exactly as before. If it does, the inspector is built from a cached model of the type, one property at a time, through a fixed chain of handlers. Every edit goes through SerializedProperty, so undo, prefab overrides and multi-object editing keep working.

  1. Model. TypeModel lists a type's serialized fields in Unity's order, plus any field, property or method that has an attribute. It is built once per type with reflection and cached.
  2. Handlers. Each attribute maps to a handler class found through TypeCache. A property gets one handler instance per attribute, created when the inspector is built.
  3. Build. Group handlers place the property, the highest-priority field handler draws it (the default is PropertyField, so existing property drawers keep working), decorators wrap it, and validators get a message area under it.
  4. Refresh. After a change, conditions are re-evaluated with compiled getters, validation runs, and only elements whose state changed are touched. Nothing is rebuilt, except when a list changes size or a [SerializeReference] changes type.

Attributes

All attributes live in the SMPro.Inspector namespace. Member names are best passed with nameof; a name can also be negated ("!flag") or nested ("settings.enabled"), and is looked up on the field's own class first, then on the classes that contain it.

C#
using SMPro.Inspector;

public class Spawner : MonoBehaviour
{
    [BoxGroup("Wave")] public bool useCurve;
    [BoxGroup("Wave"), ShowIf(nameof(useCurve))] public AnimationCurve countCurve;
    [BoxGroup("Wave"), HideIf(nameof(useCurve)), MinValue(1)] public int count = 5;

    [Required, AssetsOnly] public GameObject prefab;
    [ValueDropdown(nameof(SpawnPoints))] public string spawnPoint;

    [Button(ButtonSize.Large)] void SpawnNow(int extra = 0) { }
    IEnumerable<string> SpawnPoints => new[] { "North", "South" };
}

Validation

Validators write to a ValidationReport. In the inspector, messages show under their field and update after each change. The same rules run in the project validator, where nothing is changed.

RuleBehaviour
Required(message)Object references, strings and [SerializeReference]. Tells a missing reference apart from an empty one.
ValidateInput(method, message, type)Method returns bool or a message string; it may take the field's value.
MinValue, MaxValueNumbers and vectors. Clamp in the inspector, report in a scan. Limits can be members.
AssetsOnly, SceneObjectsOnly, ChildrenOnlyWhere a reference may live. AssetsOnly also hides scene objects from the picker.
ISelfValidatorRules across fields on a component, ScriptableObject or nested class. Messages go to the named field or the top.
C#
public class EnemyProfile : ScriptableObject, ISelfValidator
{
    [MinValue(1)] public int maxHealth = 100;
    public int startingHealth = 100;

    public void Validate(ValidationReport report)
    {
        if (startingHealth > maxHealth) report.Error("Starting health is above max health", nameof(startingHealth));
    }
}

Fields hidden by a condition are not validated. A referenced asset that implements ISelfValidator is validated on its own, not through the field that points at it. A validator that throws becomes an error message.

Project validator

Window ▸ SMPro ▸ Validator scans open scenes, scenes in the build list, prefabs and ScriptableObjects in chosen folders. It reports rule failures, attribute misuse (for example a ShowIf naming a member that doesn't exist), missing scripts and [SerializeReference] data whose class is gone. Click a result to select the object.

C#
ValidationResult result = SMValidator.ValidateProject(new ValidationOptions { folders = new[] { "Assets/Data" } });
ValidationReport report = SMValidator.Validate(someComponentOrAsset);
Shell
Unity -batchmode -projectPath . -executeMethod SMPro.Inspector.EditorTools.SMValidator.RunFromCommandLine

The command exits with code 1 when there are errors. Turn on Validate before build in the settings to run the same scan before every build.

Lists, dictionaries and references

A list is drawn by the package when its element class uses SMInspectorPro attributes, or when the field has ListSettings or TableList. Each element is built with the full handler chain, so conditions, validators and pickers work inside elements. Other lists stay Unity's.

C#
[ListSettings(ElementLabel = nameof(Wave.name), Draggable = true)] public List<Wave> waves;
[TableList] public List<Drop> drops;
public SerializableDictionary<string, int> scoreTable = new();
[SerializeReference, TypePicker] public IEffect onHit;
[InlineEditor] public EnemyProfile profile;
  • Adding, removing, moving, undo and changes made in code rebuild the inspector, on the next frame while it is open.
  • SerializableDictionary<TKey, TValue> stores its entries as a list, which is the saved data. The lookup is rebuilt from it, and the first of any duplicate keys wins. The list is only rewritten after code changes it, so a duplicate key typed in the inspector is reported, not dropped.
  • TypePicker lists every concrete [Serializable] type that fits the field. A chosen object whose class uses SMInspectorPro attributes is drawn by the package.
  • InlineEditor shows the referenced object's inspector under the field. It won't show an object inside itself, and it stops at three levels of nesting.

Tool windows

SMEditorWindow

Derive from it and add fields and buttons. The window draws itself with every attribute, with undo and validation, and without the script field.

SMMenuWindow

A searchable tree menu on the left and the selected object's inspector on the right. Fill it by path or with every asset of a type.

C#
public class EnemyDatabase : SMMenuWindow
{
    [MenuItem("Tools/Enemy Database")] static void Open() => GetWindow<EnemyDatabase>();

    protected override void BuildMenu(MenuTree tree)
    {
        tree.AddAllAssetsOf<EnemyProfile>("Enemies");
        tree.Add("Settings/Balance", balanceAsset);
    }
}

Quick start

  1. Add using SMPro.Inspector; to a MonoBehaviour or ScriptableObject.
  2. Put attributes on its fields and methods. The inspector changes on the next compile; there is no editor class to write.
  3. Open Window ▸ SMPro ▸ Validator and press Validate to check the whole project.
  4. To keep your own custom editor and still use the attributes, derive it from SMInspectorEditor.

Extend it

An attribute is a class deriving from InspectorAttribute in a runtime assembly; its handler is a class in an editor assembly with [AttributeHandler(typeof(...))]. The handler kind decides its stage.

Base classOverrideUse it for
FieldHandler<T>CreateField(), PriorityDrawing the value. Return null to keep the default field.
DecoratorHandler<T>Decorate(field), OrderWrapping the field.
StateHandler<T>Apply(ref PropertyState)Visibility and enabled state.
ValidatorHandler<T>Validate(report)Rules that also run in project scans.
GroupHandler<T>CreateGroup(), ContentFor(child)New layout groups.
C#
// Runtime assembly
public sealed class EvenAttribute : InspectorAttribute { }

// Editor assembly
[AttributeHandler(typeof(EvenAttribute))]
public sealed class EvenHandler : ValidatorHandler<EvenAttribute>
{
    public override void Validate(ValidationReport report)
    {
        if (Property.SerializedProperty.intValue % 2 != 0) report.Error($"{DisplayName} must be even");
    }
}

Handlers can resolve member names with ResolveValue<T> and ResolveCondition, report misuse with ReportProblem, and ask for a rebuild with RequestRebuild. A handler that throws falls back to the default field with a message, and the error is logged once.

The 40 built-in attributes use the same public API as your own. Registering a handler for a built-in attribute in your project replaces the built-in handler. Nothing in the runtime assembly depends on the editor, and no built-in type is required in your data except SerializableDictionary where you choose to use it.

Good to know

  • One fallback editor per type. Unity allows only one fallback editor. With another attribute package that also uses one installed, only one wins; turn ours off in the settings if needed.
  • Member order. Buttons and ShowInInspector members come after the fields of their class; use PropertyOrder to move them.
  • Name clash. SMPro.Inspector.FilePath has the same name as UnityEditor.FilePath. Editor code that imports both namespaces must write one of them in full.
  • Nested structs. Buttons on a method of a nested struct run on a copy, so their changes aren't saved; use a class.
  • Editing non-serialized values is read-only in 1.0; editing in Play mode is planned for 1.1, along with the 38 extra attributes in the design document.
